# Adaptive cache and current-head benchmark: P7

This record profiles commit `feature/adaptive-cache-optimization` after the
PD1–PD6 local freeze. It uses the release binary, a real Go corpus at
`E:\luthfi\project\go-practice`, and the Flowpeek corpus at
`E:\luthfi\project\flowpeek`. The benchmark virtual environment is local to
the Codex work area and contains `tiktoken 0.13.0`; it is not part of the
repository or the product runtime.

## Debug finding and fix

The first automatic Windows Go invocation previously probed every installed WSL
distribution even when `go.exe` was already available on Windows. A cold
`go version` profile measured 13,384.751 ms. The cache hit was 122.034 ms, but
that was still slower than raw Go at 56.693 ms.

P7 makes the WSL probe lazy. A lightweight cache entry records whether its WSL
probe is complete. Automatic Windows Go execution first checks its Windows
provider; WSL is probed only when Windows Go is unavailable or when a diagnostic
command (`resolve`, `doctor`, or setup) needs complete cross-host evidence.

Two independent post-change `go version` profiles measured cold WAD startup at
439.464 ms and 1,368.641 ms, a 89.8% to 96.7% reduction versus the original
13,384.751 ms probe. Their warm WAD medians were 101.515 ms and 150.762 ms;
raw Go was 43.306 ms and 74.123 ms respectively. Startup varies on this Windows
host, but both runs remove the expensive all-distro WSL probe. The cache does
not make compact Go commands faster than direct raw Go.

## Current-head Go benchmark

Five warmed, rotated real-corpus samples used raw Go, stock Windows RTK, WAD
auto, and an explicit WAD-native candidate. All commands exited successfully.

| Variant | Median ms | Output tokens |
| --- | ---: | ---: |
| Raw Windows Go | 654.266 | 24 |
| Stock Windows RTK | 739.137 | 7 |
| WAD auto | 735.296 | 24 |
| WAD native candidate | 748.539 | 7 |

The candidate remains 94.273 ms slower than raw for this warmed corpus but
reduces output by 70.8%. The generated narrow `go:test-all` policy therefore
continues to select native RTK under the documented 25% token-saving threshold;
all other Go forms remain raw.

## Current-head Flowpeek benchmark

Ten rotated samples per variant produced the following medians.

| Workload | Raw ms / tokens | WAD auto ms / tokens | Token saving |
| --- | ---: | ---: | ---: |
| `git status --short --branch` | 99.440 / 7 | 287.663 / 7 | 0.0% |
| `git log --oneline -100` | 107.330 / 1,309 | 228.357 / 1,309 | 0.0% |
| focused `rg` | 98.511 / 16,466 | 230.259 / 5,239 | 68.2% |
| broad `rg` | 107.221 / 248,209 | 322.200 / 5,869 | 97.6% |

The generated policy keeps compact Git reads raw and selects native RTK for the
verified `rg` family. The policy is local evidence; it is not installed into a
user's active state directory by this record.

## Automatic switching contract

WAD can switch automatically on the next invocation after a benchmark policy
is explicitly imported with `rtk-wad policy import <file>`. A policy chooses
native RTK when its warmed candidate is faster than raw, or when verified token
savings meet the 25% threshold. It keeps raw otherwise.

WAD does not silently rerun arbitrary commands as raw in the background to
"learn" a new route. That would duplicate work, distort side effects, and make
one-sided latency data unsafe. Cache state is an accelerator, not independent
performance evidence. Only read-only command families with repeated benchmark
evidence can receive a policy entry.

## Reproducing the cache profile

```powershell
.\benchmarks\run-provider-cache-profile.ps1 `
  -Wad C:\tools\rtk-wad.exe `
  -RawGo 'C:\Program Files\Go\bin\go.exe' `
  -Output .\benchmarks\results\go-provider-cache.json
```

The JSON artifact is local and ignored by Git. It is a latency diagnostic only;
token-routing policy remains generated by the real-corpus three-way runner.
